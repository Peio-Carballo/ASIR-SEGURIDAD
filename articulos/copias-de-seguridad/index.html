01 / Copias de seguridad12 septiembre 20264 min de lectura

Un backup no se da por bueno.
Se prueba.

Tener una copia es el principio. Lo que importa es poder recuperar los datos y volver a poner el servicio en marcha.

El mensaje verde no lo demuestra todo

Un trabajo de backup puede terminar sin errores y, aun así, no ser suficiente para recuperar una aplicación. Quizá falte su base de datos, no tengamos la clave de descifrado o no sepamos cómo arrancarla en otro equipo.

Por eso he elegido este tema: conecta directamente la seguridad con la disponibilidad. CISA recomienda comprobar periódicamente la integridad y la recuperación de las copias, además de mantener copias cifradas fuera de línea. Un ransomware puede intentar borrar o cifrar los backups a los que tenga acceso. [1]

Repartir el riesgo: la regla 3-2-1

INCIBE explica esta estrategia como una forma de evitar que un único fallo afecte a toda la información. La idea es mantener varias copias y separarlas. [2]

Dos carpetas en el mismo disco no eliminan el riesgo de que ese disco falle. También conviene separar los accesos: si la misma cuenta puede borrar el original y todas las copias, el problema sigue estando demasiado cerca. El aislamiento y las pruebas de recuperación complementan la estrategia. [1]

¿Cuántos datos perdería? ¿Cuánto tardaría?

Son dos preguntas diferentes. El RPO expresa cuánta pérdida de datos, medida en tiempo, se acepta. El RTO es el tiempo máximo aceptable hasta restablecer el servicio. Ambos son objetivos: hay que comprobar que el sistema puede cumplirlos. [3]

Ejemplo hipotético

Una web tiene su última copia válida de las 02:00 y falla a las 16:00. Si no hay otro punto de recuperación, podría perder hasta 14 horas de cambios. Si vuelve a funcionar a las 17:30, la recuperación habrá durado 1 hora y 30 minutos.

Esos son resultados del ejemplo, no los objetivos RPO y RTO. Para saber si son aceptables, primero habría que fijar cuánto puede asumir esa web.

La prueba que propondría en clase

Haría una práctica con una web de prueba y datos ficticios. No hace falta provocar una caída en un servicio real para aprender a recuperarlo.

  1. Preparar la copia. Guardar los archivos, la base de datos y la configuración necesaria.
  2. Restaurar en una máquina aislada. Usar otra VM, sin sobrescribir el entorno original ni enviar correos o tareas a servicios reales.
  3. Comprobar el servicio. Abrir la web, acceder con un usuario de prueba y revisar un registro conocido.
  4. Anotar el resultado. Fecha de la copia, tiempo empleado, datos recuperados y errores encontrados.

Esta es una propuesta de laboratorio; todavía no representa una práctica realizada. Repetiría la prueba después de cambios importantes para comprobar que las instrucciones siguen sirviendo.

Mi reflexión

Me parece fácil confiarse cuando el panel muestra todo en verde. Yo preferiría una estrategia sencilla que sepa restaurar antes que una configuración muy completa que nunca haya probado.

La pregunta que me quedo es: si mañana falla el servidor, ¿sé qué recuperar, dónde está y cuánto voy a tardar?

Para mí, ahí está la relación con alta disponibilidad: un backup ayuda a recuperar información, pero no evita por sí solo que el servicio se caiga. Hay que pensar tanto en prevenir la interrupción como en salir de ella.
